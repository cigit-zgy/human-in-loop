### Real MCP/iMessage attempts and exact blocker

All real attempts used an actual stdio MCP protocol client against the installed `human-in-loop` server. They were not internal Rust calls, direct coordinator calls, or direct `imsg` invocations.

1. The first real call initialized correctly and entered the production `ask_human` path, but the channel returned `NoAvailableChannel` with structural state `imessage: send_failed`. The User confirmed that no phone message arrived. There was no resolved chat and no watcher, so the mutation was classified `not_started`; this justified one controlled recovery attempt under the task's no-blind-retry rule.
2. Normal macOS Automation consent was then attempted in the Bot session. After subsequent final-binary installation and Full Disk Access repair, the controlled MCP retry again returned `NoAvailableChannel` at the send stage. The User again reported no receipt. No further retry was made.

The second failure is explained by current TCC evidence:

- Unified TCC logging for the failed production send identifies `/Users/Shared/human-in-loop/bin/human-in-loop` as the responsible AppleEvents client targeting Messages.
- The designated requirement bytes for that responsible binary changed when the release binary was rebuilt/replaced after the earlier consent interaction.
- The Bot user's TCC store has no durable AppleEvents authorization row for the current final worker identity.
- A redacted, non-message-producing structural probe in the Bot session reports Automation denied or unavailable.
- Full Disk Access remains allowed, so this is not a Messages database permission failure.

Consequently the current final installed worker still requires normal macOS `Automation → Messages` approval in the Bot graphical session. The task explicitly forbids database injection or other TCC bypasses. The existing `bootstrap_required` health result is therefore incomplete as a readiness assertion: it proves the external executable, resource bundle, Bot database access, configuration, and absence of a deterministic chat, but it does not prove current AppleEvents authorization.

No genuine incoming iPhone notification was presented, no token/option reply was available, no strict correlated reply was accepted, no `selected_choice_id` was returned, and no real terminal winner can be claimed. The real qualification is therefore not PASS.
