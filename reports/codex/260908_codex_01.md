# Dedicated Bot Apple Account production topology — Codex report

## Verdict and resolved design gap

**VERDICT: PASS.** The design gap was unreliable iPhone notification presentation for same-account self-messages. The accepted resolution is a production topology with a dedicated `human-in-loop` macOS user and an independent Bot Apple Account that sends genuine incoming iMessages to the User's personal Apple Account.

Same-account correlation may remain for development/diagnostic compatibility, but it cannot establish production `ready`, release qualification, or notification qualification. No new unresolved `DESIGN_GAP` was found within the frozen scope.

## Accepted topology

```text
Guangyao Zhao macOS user
├── personal Apple Account and Messages.app unchanged
├── Codex / Agent
└── main human-in-loop coordinator
          ↓
    narrow authenticated local IPC
          ↓
human-in-loop macOS user
├── independent Bot Apple Account in Messages.app
├── Bot transport worker
└── Bot-owned imsg
          ↓
      iMessage only
          ↓
personal iPhone / personal Apple Account
```

`design/00_overview.md` owns the whole-system `sender_account != recipient_account` invariant. `design/03_imessage_channel.md` owns the sender/recipient evidence, session readiness, health-state consequences, cross-user boundary, strict correlation, and Apple Messages release qualification.

The main coordinator does not directly read the Bot user's Messages database, launch its `imsg`, or automate its Messages.app across UID boundaries. A future Bot user-session worker is reached only through narrow authenticated local IPC; the concrete IPC protocol and service implementation were intentionally not selected in this design freeze.

## Health states

The design preserves existing states and freezes the new production identity/session states:

```text
not_configured
BOT_SESSION_LOGIN_REQUIRED
BOT_MESSAGES_ACCOUNT_UNAVAILABLE
BOT_SENDER_IDENTITY_UNVERIFIED
SELF_MESSAGE_UNSUPPORTED
imsg_missing
permission_missing
messages_unavailable
bootstrap_required
recipient_not_imessage
watch_failed
send_failed
ready
```

`SELF_MESSAGE_UNSUPPORTED` is determined before mutation when verified sender and recipient identities belong to the same Apple/iMessage account topology. It prevents production readiness and directs the User to the dedicated Bot Apple Account.

`ready` requires the dedicated Bot macOS user/session, active Bot Messages account, verified Bot sender and recipient identities, distinct-account evidence, deterministic direct conversation, proven iMessage service, available `imsg`, and required permissions. `bootstrap_required` remains an explicit first-use state and may use the first real structured confirmation only after all non-chat prerequisites pass.

## Reboot and session lifecycle

First setup remains manual: create/confirm and log in to `human-in-loop`, sign Messages into the existing second Apple Account, confirm iMessage activation, grant Full Disk Access and Automation → Messages normally, then Fast User Switch back to `Guangyao Zhao`.

Sleep and lock do not require another Bot login. Fast User Switching may preserve service while the Bot graphical session stays logged in. Reboot is a hard boundary: saved Apple credentials do not imply a restored graphical session. Before the first post-reboot Bot login, Apple Messages reports `BOT_SESSION_LOGIN_REQUIRED` with an explicit log-in-once/Fast-User-Switch-back instruction. Feishu may continue independently when it is ready.

## Notification checkpoint and iMessage safety

Production Apple Messages release qualification now includes `HUMAN_NOTIFICATION_CHECKPOINT`. With the iPhone locked or Messages not foreground, notifications enabled, and Focus/DND not suppressing the test, the User must explicitly confirm a lock-screen notification or banner. Evidence records:

```text
notification_presentation = HUMAN_VERIFIED
```

Audible or haptic perception is optional observation, not a hard automated assertion. The same E2E must prove Bot-to-personal incoming iMessage, one application mutation, actual outgoing iMessage service, User reply, strict correlation, one canonical choice, and watcher cleanup.

The send contract remains explicitly:

```text
imsg send --service imessage --no-sms-fallback
```

No `auto`, SMS, MMS, RCS, carrier relay, paid gateway, or fallback was authorized. Unprovable actual outgoing service fails closed.

## Privacy model

The project may retain only necessary transport metadata such as Bot sender handle, recipient handle, chat identity, observed service, and health/session state. Apple passwords, 2FA codes, trusted-phone credentials, Apple session secrets, and unrelated Messages history remain outside the project.

The concept recommends disabling unrelated Bot-account iCloud surfaces. Messages in iCloud is not required for a single-Mac transport host. No private recipient, token, chat identity, credential, or Messages content was introduced into tracked artifacts.
