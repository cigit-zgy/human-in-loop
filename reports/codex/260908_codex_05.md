## Release-gate defect and repair

The first installed health check exposed a real unattended-operation regression.
`channel test imessage` loaded the complete configuration and therefore attempted
to read the unrelated Feishu secret from Keychain. After replacing the signed
v0.1.0 binary, that unnecessary read launched macOS SecurityAgent and blocked the
iMessage-only no-message health check before it reached the dedicated worker.

This was classified as `IMPLEMENTATION_DRIFT`: current design already requires a
prepared host to operate without recurring administrator/Keychain prompts.
Codex stopped the task-owned blocked command, made no Keychain ACL or permission
change, and used test-driven repair:

1. Added `channel_health_loads_secrets_only_for_feishu`; it first failed because
   the loader boundary did not exist.
2. Routed Feishu health through `AppConfig::load()` and iMessage health through
   `AppConfig::load_without_secrets()`.
3. Rebuilt, stable-signed, atomically reinstalled, updated the prepared shared
   worker without sudo, and reran all materially affected release gates.

The repaired installed command returned `ready` immediately, and the full macOS
status returned `Setup COMPLETE` with all ten readiness/qualification rows green.
No production certificate, private key, login keychain, default keychain, search
list, or credential was changed.

An earlier MCP synthetic run also failed before daemon startup because Codex put
its scratch under an unnecessarily long nested path and exceeded macOS Unix
socket `SUN_LEN`. This was a `TEST_DEFECT`, not a product defect. The identical
verifier passed from the task-authorized short root; no production code was
changed for that invocation error.
