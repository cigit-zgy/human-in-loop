# Context / problem

The current project already provides a production-qualified local MCP `ask_human` control surface over the canonical confirmation coordinator. The missing concern is not another confirmation transport; it is **machine-wide Codex policy and lifecycle integration**.

The desired behavior is:

```text
all Codex repository tasks
→ know when human input is mandatory
→ stop at that checkpoint
→ use canonical human-in-loop instead of guessing
→ resume only from one valid correlated human decision

all normal Codex terminal states
→ produce the normal task result/report first
→ notify the user through human-in-loop
→ terminate without requiring a second acknowledgement
```

This behavior must apply across projects without copying the full AskHuman protocol into every project `AGENTS.md` or every task.

# Prior-art / platform basis

Current OpenAI Codex documentation states that Codex aggregates user instructions from `$CODEX_HOME/AGENTS.override.md` / `$CODEX_HOME/AGENTS.md` and then more specific project-scoped instruction files. This makes the Codex-home AGENTS layer suitable for a thin machine-wide activation rule while project AGENTS files remain the owner of project-specific checkpoints.

Source:

- https://openai.com/index/unrolling-the-codex-agent-loop/

Disposition: **REFERENCE_ONLY**.

Design consequence: use `$CODEX_HOME/AGENTS.md` for the global activation/fail-closed invariant, not for a copied full human-in-loop manual.

## OpenAI Codex MCP tool integration

OpenAI's current Codex harness documentation states that MCP servers can provide tools to the Codex agent loop; those MCP tools are not governed by the Codex shell sandbox and must enforce their own guardrails.

Sources:

- https://openai.com/index/unrolling-the-codex-agent-loop/
- https://openai.com/index/unlocking-the-codex-harness/

Disposition: **REFERENCE_ONLY**.

Design consequence: register the maintained `human-in-loop` MCP server in Codex configuration and keep safety/correlation/transport constraints inside `human-in-loop` itself.

# User + ChatGPT adjudication

## 1. Machine-wide activation belongs in Codex-home AGENTS

Accepted architecture:

```text
$CODEX_HOME/AGENTS.md
= thin global activation + hard fail-closed rule

human-in-loop SKILL.md
= generic checkpoint classifier + ask/notify lifecycle semantics

project AGENTS.md
= additional project-specific checkpoints

reports/chatgpt task
= additional task-specific checkpoints
```

The root Codex AGENTS layer MUST NOT duplicate the full Skill or project policy. It identifies the maintained Skill authority and requires Codex to obey it for every task.

More specific project/task instructions may add human checkpoints. They may not silently bypass a checkpoint required by the global human-in-loop contract unless the User explicitly overrides it.

## 2. Tool availability belongs in Codex config, not AGENTS

The machine integration is split intentionally:

```text
$CODEX_HOME/AGENTS.md
→ policy: when human-in-loop is mandatory

$CODEX_HOME/config.toml
→ capability: register/expose maintained human-in-loop MCP server
```

`AGENTS.md` cannot substitute for an unavailable MCP tool. MCP registration/configuration cannot substitute for the decision policy.

## 3. Blocking decision and terminal notification are different semantics

The maintained MCP surface becomes:

```text
ask_human
= blocking human decision
= waits for one canonical correlated result
= execution cannot cross the checkpoint without that result

notify_human
= non-blocking human notification
= used for terminal task reporting
= does not require a reply
= does not reopen or prolong a completed task
```

The two capabilities may reuse the same configured Feishu/iMessage delivery infrastructure, but they do not share result semantics.

## 4. Generic ASK_HUMAN_REQUIRED classifier

A human decision is required when at least one of the following is true and the action has not already been explicitly authorized by a higher/current authority:

```text
EXPLICIT_CHECKPOINT
= User, project AGENTS, current design, or committed task explicitly requires confirmation

USER_PREFERENCE_DECISION
= multiple materially valid outcomes exist and the correct choice depends on User preference rather than existing authority

DESTRUCTIVE_OR_IRREVERSIBLE
= deletion/overwrite/migration or another action can materially destroy or replace shared/persistent state and is not already explicitly authorized

EXTERNAL_OR_PUBLIC_SIDE_EFFECT
= publication/release/send/public visibility/external creation or another meaningful outside-world effect requires User authorization and is not already authorized

AUTHORITY_OR_SCIENTIFIC_CHANGE
= current design/scientific/product/trust semantics must be reopened or changed

SECURITY_CREDENTIAL_PERMISSION
= credentials, permissions, security boundaries, or sensitive access must be changed or newly granted
```

Do **not** ask merely because there is a routine reversible implementation choice that current design/task authority already resolves. Human-in-loop is a decision boundary, not a substitute for engineering judgment.

Codex shell/sandbox permission prompts remain host permission mechanics and are not redefined as semantic `ask_human` decisions.

## 5. Checkpoint lifecycle is fail-closed

```text
ASK_HUMAN_REQUIRED
→ construct canonical structured request
→ call ask_human
→ pause affected execution path
→ wait for exactly one valid correlated result
→ continue only with the selected semantic choice
```

Forbidden substitutes:

```text
default choice
timeout choice
guessed preference
ordinary terminal prompt while bypassing the required MCP checkpoint
free-form reply parsing that bypasses canonical result correlation
```

If `ask_human` or the required human-in-loop runtime is unavailable at a mandatory checkpoint:

```text
→ BLOCKED
→ do not cross the checkpoint
→ report the unavailable capability explicitly
```

## 6. Every normal terminal task state attempts a human notification

After the task's durable result is complete and any required repository push/fresh-fetch equality has succeeded, Codex attempts one compact terminal notification for:

```text
PASS
PASS_WITH_LIMITATIONS
BLOCKED
FAIL
```

The notification contains only enough information for the user to understand the outcome and locate durable evidence, for example:

```text
project
task_id when available
verdict
short summary / blocker
branch + commit or report locator when available
```

It must not paste a full Codex report or task body into the phone message.

## 7. Terminal notification is best-effort and must not falsify task verdict

A terminal notification failure occurs **after** task execution semantics have already reached their terminal result.

Therefore:

```text
TASK_VERDICT: PASS
notify_human fails
→ task remains PASS
→ HUMAN_NOTIFICATION: FAILED is surfaced in the local final response/report evidence
```

Do not change a scientifically or mechanically valid task result into FAIL merely because the notification service is unavailable.

A bounded notification retry may be implemented when justified; no indefinite retry/wait loop is allowed.

## 8. Remote skill authority and local discovery are separate

`human-in-loop` is a first-party, GitHub-maintained capability. The durable Skill authority is an immutable repository coordinate:

```text
cigit-zgy/human-in-loop@<accepted-commit>:SKILL.md
```

A local Codex discovery entry may expose that Skill, but the path/symlink itself is not authority. The machine-wide AGENTS rule should identify the immutable Skill coordinate or a local copy proven equal to it.

# Design consequence

Accepted result:

```text
UPDATE design_id=mcp-interface
NEW_TOPIC design_id=codex-integration
NEW operational projection: SKILL.md
```

The current living design must therefore:

1. extend `design/05_mcp_interface.md` from one public decision tool to two narrowly separated tools: `ask_human` and `notify_human`;
2. add `design/06_codex_integration.md` for machine-wide activation, checkpoint classification, terminal reporting order, and failure semantics;
3. add a repository-root `SKILL.md` that operationalizes the accepted generic Codex-facing lifecycle without duplicating transport internals;
4. keep project-specific checkpoint additions in each project's own `AGENTS.md` / committed task;
5. delegate local `$CODEX_HOME/AGENTS.md`, `$CODEX_HOME/config.toml`, local Skill discovery, MCP runtime installation, and real end-to-end qualification to Codex because those depend on the User's machine.

No GitHub relay, polling workflow, second coordinator, second request model, or task-specific confirmation special case is accepted.
