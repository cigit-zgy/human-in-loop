# Problem

The dedicated Bot-user topology is correct, but the first implementation repeatedly requested macOS permissions and ultimately failed at Automation → Messages. The final installed worker was ad-hoc signed and rebuilt/replaced after an earlier consent interaction, so macOS no longer considered it the same AppleEvents requester. The same identity churn also explains repeated protected-folder prompts such as access to Documents.

The user additionally requires operational simplicity:

- do not repeatedly switch between `Guangyao Zhao` and `human-in-loop` except for Apple GUI actions that truly require the Bot session;
- do not repeatedly ask for an administrator password during one setup run;
- grant each macOS privacy permission once to the final stable runtime identity, then keep it valid across rebuild/install cycles where possible.

# Platform evidence

Apple's TN3127 explains that macOS privacy grants are tracked through a code object's designated requirement (DR). Ad-hoc signed code has a DR tied to that specific version, so rebuilding or replacing it can cause macOS to treat the next binary as new code and request authorization again. Distribution/development signing with a stable signer and identifier gives successive builds a compatible identity.

Apple also treats Files & Folders, Full Disk Access, and Automation/Apple Events as separate consent gates. Administrator/root privileges do not substitute for TCC user consent.

Apple exposes `AEDeterminePermissionToAutomateTarget` to query AppleEvents Automation authorization and optionally trigger consent; this provides a non-message readiness path rather than discovering missing Automation only during the first real send.

`openclaw/imsg` documents that Full Disk Access and Automation belong to the process context that actually runs `imsg`. Indirect launches through a terminal, wrapper, SSH session, editor, or gateway can shift the responsible process. Its documentation also notes stale grants after parent-app replacement.

OpenClaw's iMessage deployment guide reaches the same conclusion operationally: run the Gateway/`imsg` in the signed-in Messages user's session, and grant Full Disk Access and Automation from that same process context. Its SSH-wrapper troubleshooting documents `-1743` AppleEvents failures where reads work but sends cannot be authorized; the recommended recovery is a local same-session LaunchAgent/process context rather than repeated wrapper retries.

Additional open-source macOS projects such as FinderJump, Loudini, Tessera, and OpenSuperMLX independently use a stable local code-signing certificate for development builds specifically so TCC grants survive rebuilds. This is reference evidence, not a new runtime dependency.

# Alternatives considered

## Continue ad-hoc signing and re-approve after each rebuild

Rejected. It directly recreates the observed failure mode and makes release qualification non-repeatable.

## Give Codex a long-lived unrestricted root shell

Rejected. `sudo` cannot grant Automation or TCC permissions, and a persistent arbitrary root shell unnecessarily widens the trust boundary.

## Repeatedly switch to the Bot user and run terminal commands manually

Rejected as the normal workflow. Only Apple Account login/activation and macOS privacy consent that genuinely require the Bot graphical session should require switching.

## Stable runtime identity + one-time bootstrap

Accepted.

# Accepted strategy

## Stable code identity

The installed `human-in-loop` runtime must have a stable macOS code identity across development reinstall cycles.

Preference order for this single-machine local deployment:

1. use an existing suitable Apple Development / Developer ID code-signing identity when explicitly configured;
2. otherwise create one machine-local self-signed Code Signing certificate dedicated to `human-in-loop` and store its private key only in the local macOS Keychain;
3. ad-hoc signing is not acceptable for the production Bot worker once TCC grants are part of readiness.

The signing certificate/private key is never committed to Git and is not part of human-in-loop configuration.

The installed runtime keeps fixed code identifiers. Installation records the final designated requirement and verifies that future replacements satisfy the same expected identity before they are activated. A replacement that changes the expected DR must stop and require an explicit permission migration rather than silently invalidating TCC grants.

## One-time privileged bootstrap

System-level bootstrap work is concentrated into one bounded setup operation. The user may authenticate administrator privileges once for that operation. The implementation may validate/cache sudo authorization for the bounded bootstrap, but it must not leave Codex with a persistent unrestricted root shell.

After first setup, normal build/install/runtime operations should not require repeated administrator-password prompts unless a real system-level change is requested.

## Privacy/TCC bootstrap

TCC remains a user-consent flow and is separate from sudo.

The final installed stable identity is established first. Only then does the Bot-user session run a permission bootstrap/preflight through the same worker/process context that production sends use.

The bootstrap must prove, without sending a real message:

- Bot user session exists;
- Bot Messages account is active;
- required Messages database access is available;
- Automation → Messages is allowed for the exact final responsible process identity.

Automation is checked with a non-mutating AppleEvents permission/preflight path (for example `AEDeterminePermissionToAutomateTarget` or an equivalent documented same-context check). A real iMessage send must not be used merely to discover whether Automation permission exists.

`bootstrap_required` is valid only after Automation readiness and all other non-chat prerequisites are proven. Missing Automation reports a dedicated actionable permission state before any real send.

## Minimal user switching

Normal operation occurs from the primary `Guangyao Zhao` session through authenticated local IPC to the Bot-user LaunchAgent/worker.

User switching is required only for actions that genuinely belong to the Bot graphical session, primarily:

- first Apple Account / Messages login and iMessage activation;
- first TCC consent interaction when macOS requires the Bot user to approve it;
- post-reboot Bot login as already defined by the current Bot-session lifecycle;
- recovery when Apple/macOS invalidates one of those user-owned states.

Codex must not request a user switch for ordinary worker install, health checks, message requests, log inspection, or deterministic tests when those operations can be performed safely through the existing worker/IPC boundary.

## Protected folders

The production Bot worker is installed under `/Users/Shared/human-in-loop` and must not read the source repository or other protected Documents paths. The primary coordinator only accesses a repository path when the caller explicitly supplies it for repository identity/context; it must not recursively scan protected user folders as ambient discovery.

If the primary runtime needs Documents access, permission is granted once to its stable code identity. Repeated Documents prompts after the stable identity is established are treated as a defect, not normal operation.

# Design consequence

Add a current `macos-runtime-deployment` living-design topic for stable signing, privilege bootstrap, TCC ownership, and user-switch policy. Keep iMessage transport semantics in `imessage-channel`; it consumes the deployment readiness result and must not report `bootstrap_required` before Automation readiness is established.
