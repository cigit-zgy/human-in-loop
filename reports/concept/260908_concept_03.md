# Context

The maintained product now has real evidence for the complete local path:

```text
Codex / MCP
→ human-in-loop coordinator
→ dedicated human-in-loop macOS-user worker
→ distinct Bot Apple Account
→ explicit iMessage-only send
→ locked iPhone notification
→ structured reply
→ strict correlation
→ one canonical result
```

The dedicated Bot-user topology is accepted. Stable local code signing, a bounded administrator bootstrap, non-message Automation preflight, and a real distinct-account notification/reply qualification have also passed on the development host.

The remaining product question is therefore not whether the architecture works, but what interaction burden is acceptable for an open-source user after installation.

# Observed development friction

Development qualification required repeated rebuilds, process-identity changes, TCC recovery, temporary user switching, and administrator authentication. Those actions were useful while discovering the correct deployment model, but they are not acceptable as normal product behavior.

The product exists specifically so the User can make remote decisions while away from the Mac. A runtime that requires a person to return to the computer for ordinary password entry, user switching, Documents access, Full Disk Access, or Automation consent would defeat that purpose.

# Accepted onboarding model

Interactive setup is concentrated into one explicit onboarding phase.

The User owns the actions that cannot or should not be automated:

```text
create the dedicated macOS user (default documented name: human-in-loop)
log in to that user once
sign Messages.app into a distinct Bot Apple Account
complete Apple Account / 2FA interaction only in Apple UI
grant the final stable runtime the required macOS privacy permissions
perform the initial real notification qualification
```

The project owns the repeatable setup around those checkpoints:

```text
install stable signed runtime
prepare shared paths and worker ownership
perform one bounded administrator bootstrap
install/restart the Bot-user worker
run no-message health and Automation preflight
show one consolidated readiness result
```

# SETUP_COMPLETE

The installation is not production-ready until the setup command can prove all required predicates and records a local setup-complete state derived from current health, not from an unchecked boolean.

Conceptually:

```text
stable runtime identity              READY
Bot macOS user                       READY
Bot graphical/login session          READY
Bot Messages account / iMessage      READY
Bot sender and recipient distinct     READY
Full Disk Access / DB access          READY
Automation → Messages                 READY
iMessage-only routing                 READY
real incoming notification            HUMAN_VERIFIED
structured reply/correlation          VERIFIED

→ SETUP_COMPLETE
```

A partially configured installation remains in an actionable setup/recovery state and must not pretend to be production ready.

# Normal-operation contract

After `SETUP_COMPLETE`, ordinary operation is unattended.

Normal Codex/MCP tasks, health checks, notifications, confirmation sends, replies, worker restarts, and qualified routine updates must require:

```text
administrator password prompts   0
Keychain password prompts         0
Fast User Switching              0
new Full Disk Access prompts      0
new Automation prompts            0
new Documents/Files prompts       0
```

A repeated privacy prompt after the stable runtime identity was qualified is a deployment regression or recovery condition, not normal UX.

`sudo` is not a solution to TCC. Administrator authentication and TCC remain separate gates.

# Allowed recovery checkpoints

Human interaction may reappear only when the actual host state changed or Apple requires it, for example:

```text
real Mac reboot and Bot login session not yet re-established
Bot Apple Account / Messages signed out
User revoked a required TCC permission
stable local signing identity was deleted or intentionally migrated
major macOS change invalidated a previously valid grant
User intentionally changes Bot/recipient identity
```

These states must be reported explicitly and consolidated into one actionable checkpoint. Codex must not repeatedly prompt for the same unresolved permission through multiple commands.

# Open-source user experience

The public setup should optimize for a small documented manual surface rather than pretending Apple account creation/login can be automated safely.

Recommended user story:

```text
1. User creates a second standard macOS user.
2. User logs into that user and signs Messages into a separate Bot Apple Account.
3. User returns to the primary user and runs one human-in-loop setup/bootstrap command.
4. The setup command prepares the runtime and reports exactly which remaining macOS consent, if any, requires the Bot session.
5. User grants those permissions once.
6. Setup runs a final notification/reply qualification.
7. SETUP_COMPLETE is reported.
8. Ordinary use thereafter is unattended.
```

The default documented Bot-user name may be `human-in-loop`, but the product must not make that literal username a universal semantic requirement when a configurable dedicated user can satisfy the same contract.

# User + ChatGPT adjudication

Accepted:

```text
Core architecture              FUNCTIONALLY PROVEN
Dedicated Bot macOS user       PRODUCTION DEFAULT
Distinct Bot Apple Account     PRODUCTION REQUIRED
Stable signed runtime          REQUIRED
One-time bounded bootstrap     REQUIRED
Consolidated TCC onboarding    REQUIRED
Unattended normal operation    REQUIRED
Repeated permission prompts    DEFECT / RECOVERY, not normal behavior
```

Release work now shifts from architecture discovery to onboarding, recovery, packaging, documentation, default-branch integration, and final release qualification.
