# Implement minimal MCP ask_human control interface

## Mission

Implement `design/05_mcp_interface.md` as the smallest standard MCP-facing invocation surface over the already validated `human-in-loop` confirmation runtime.

The goal is:

```text
MCP client
→ ask_human
→ canonical confirmation request
→ existing coordinator
→ configured iMessage / Feishu channel(s)
→ exactly one canonical result
→ MCP client
```

Do not use GitHub issues, comments, commits, Actions, repository dispatch, or polling as the runtime confirmation transport.

## LOCAL scope

### 1. Reuse the existing runtime

Inspect the current MCP-related code already present under `src-tauri/src/mcp/` before adding anything.

Prefer extending/reusing the existing MCP server/runtime rather than introducing a second server stack or parallel request model.

Do not create a second canonical confirmation/coordinator implementation.

### 2. Expose exactly one initial mutation tool

The maintained initial MCP tool surface is exactly:

```text
ask_human
```

Do not expose unrelated legacy/internal MCP operations as part of this new public capability merely because code already exists.

Input schema must reflect the living design and stay small:

```text
repository_path      required for repository-associated requests
source_agent         required
question             required
choices              required 2–6
context              optional
recommended_choice   optional
request_id            optional
```

Choices must carry stable semantic ids and compact labels.

Do not accept transport-specific recipient/channel command arguments.

### 3. Canonical repository identity

For repository-associated requests, resolve project identity through the existing canonical GitHub-origin repository-slug logic.

The caller supplies a local `repository_path`, not a rendered repository name.

Do not trust caller-supplied arbitrary repository labels.

If the path is a Git repository but canonical GitHub identity cannot be resolved, fail closed consistently with the current renderer contract.

### 4. Canonical request/result mapping

Map `ask_human` input into the existing canonical confirmation model.

Numeric iMessage positions are not MCP semantics.

Successful MCP result must expose only transport-independent data equivalent to:

```text
request_id
selected_choice_id
source_channel_id
```

Do not expose recipient, chat id/GUID, iMessage token, raw Messages row, credential, or private transport log.

### 5. Blocking/cancellation behavior

`ask_human` is a bounded blocking MCP call over the existing confirmation lifecycle.

It waits for exactly one terminal canonical result.

Client cancellation/disconnect must cancel the active request and clean up all channel watchers/processes owned by that request.

No orphaned active request may remain after cancellation or server shutdown.

Preserve current first-valid-terminal-answer coordinator semantics if multiple configured channels participate.

### 6. Server transport

Implement the smallest standards-conforming MCP server transport that fits the existing repository architecture.

Prefer a local stdio/process transport for the first implementation and verification.

Do not add:

```text
public unauthenticated HTTP server
GitHub runtime relay
self-hosted GitHub Actions runner requirement
new cloud backend
arbitrary webhook executor
```

Keep the tool implementation transport-neutral so a future supported remote MCP / Secure MCP Tunnel deployment can reuse the same `ask_human` contract.

### 7. Security hard boundary

The MCP server must not expose:

```text
generic shell execution
arbitrary file read/write
arbitrary Messages/imsg command execution
recipient enumeration
channel credentials
raw chat database access
SMS/MMS/RCS controls
```

MCP invocation must not weaken any existing iMessage invariant.

### 8. Deterministic tests

Add focused tests for at least:


### 9. Local MCP-client E2E

Use a real MCP client or protocol-level local test client against the production MCP server.

The client must invoke `ask_human`; do not bypass the MCP tool handler and call internal Rust functions directly as the E2E substitute.

Use the User-approved private local same-account iMessage configuration already established on the Mac.

Private recipient/configuration must remain local and untracked.

Send exactly one harmless confirmation, semantically similar to:

