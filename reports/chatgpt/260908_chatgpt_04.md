### 2. Consolidate public onboarding

The public user should experience one coherent setup flow after manually completing the Apple/macOS actions the project must not automate.

Manual prerequisites remain:

```text
create a dedicated standard Bot macOS user
log into it once
sign Messages.app into a distinct Bot Apple Account
complete Apple Account / 2FA only in Apple UI
```

After those prerequisites, reuse/consolidate the existing installation/bootstrap/worker mechanisms into one documented setup path from the primary user.

Prefer the existing `scripts/install.sh`, `scripts/macos-bootstrap.sh`, worker commands, and health/preflight machinery. Add only the thinnest orchestration needed; do not create another setup framework.

The setup path must:

- determine the current primary user rather than hard-code a personal username;
- support a dedicated Bot user with documented default `human-in-loop` and allow an explicit configured alternative if the existing implementation can do so cleanly;
- collect/store only necessary non-secret sender/recipient handles through the established private local configuration owner;
- never request/capture Apple Account password or 2FA;
- use at most one bounded administrator authentication for initial protected setup;
- use the final stable requester identity before TCC qualification;
- perform no-message permission/Automation preflight before any real send;
- present one consolidated actionable checkpoint when native macOS UI interaction is still required;
- resume the same setup flow after that checkpoint;
- perform one initial notification/reply qualification before declaring setup complete.

Do not invent a second public CLI/API contract if the current installed CLI/scripts can provide one coherent documented entrypoint. If a new public command name/semantic is genuinely required and current design cannot determine it, report `DESIGN_GAP` rather than inventing an incompatible interface.
