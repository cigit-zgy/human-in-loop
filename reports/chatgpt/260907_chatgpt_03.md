## LOCAL scope

### 1. Implement the compact iMessage renderer

Conform exactly to `design/01_interaction_protocol.md`.

The preferred normal shape is:

```text
[HIL · <TOKEN>]
<source>[ · <project>]
<optional context line 1>
<optional context line 2>

<compact question>

1  <choice>
2  <choice>

Reply: <TOKEN> 1
```

Do not mechanically render empty/label-only sections.

For ordinary confirmations, remove redundant headings such as:

```text
Context
Question
Action
```

unless the current living design explicitly requires equivalent decision semantics through content rather than headings.

Implement these hard constraints:

```text
source + optional project line     <= 80 Unicode scalar values
additional context lines           <= 2
each additional context line       <= 80
question/summary                    <= 160
choices                             2–6
preferred routine choices           2–4
one choice label                    <= 60
complete rendered text hard limit   <= 700
outgoing decision images            <= 1
```

Normal compact target:

```text
approximately 300–500 Unicode scalar values or less
```

This is a target, not permission to truncate critical semantics.

Compaction order:

```text
remove optional explanatory text
→ remove optional context
→ compact source/project presentation
→ preserve decision-critical question + choices + token
→ if still > hard limit: unsupported / send nothing
```

Never silently truncate critical content.

### 2. Preserve canonical semantics

Do not change canonical request/choice identity merely to make the phone message shorter.

The numeric option remains rendering-only:

```text
<TOKEN> <OPTION_NUMBER>
→ stable canonical choice id
```

Recommended choice semantics, when present and relevant, remain preserved with compact rendering such as:

```text
1  Accept [recommended]
```

Do not introduce fuzzy reply parsing.

### 3. Preserve same-account correctness

Do not alter the already proven same-account architecture except where necessary to consume the new renderer output.

All existing strict gates remain mandatory:

```text
configured direct chat
post-send row/cursor boundary
candidate row after sent row
candidate GUID != sent GUID
exact token grammar
one active request
valid option
request not terminated
reaction/attachment rejection
reply_to_guid consistency when present
exactly one terminal winner
watcher cleanup
```

`same_account` may accept the documented self-synchronized reply under those gates. `distinct_peer` must continue rejecting self-authored messages.

### 4. Exactly one application send

Add/retain focused evidence that one canonical confirmation creates exactly one application `imsg send` mutation.

Same-account Apple synchronization may produce multiple visible bubbles/copies. Do not treat that as permission to retry or duplicate the application send.

Do not implement visual deduplication using:

```text
message delete
message unsend
private IMCore bridge
SIP disabling
dylib injection
direct chat.db mutation
Messages/iCloud setting changes
```

### 5. Preserve absolute iMessage-only boundary

Every direct mutation remains explicit iMessage-only with defense-in-depth no-SMS fallback.

No production path may enable:

```text

sms
SMS
MMS
RCS
carrier relay
paid gateway
```

Do not intentionally send a carrier-message negative test.
