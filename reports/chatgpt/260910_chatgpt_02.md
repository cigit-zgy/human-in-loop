# A. Proactive-message policy

Machine-wide default must be:

```text
real unresolved semantic decision
→ ask_human

normal terminal task state
→ at most one notify_human attempt for the logical task

ordinary progress / heartbeat / percentage-complete
→ zero proactive notifications
```

Terminal states remain exactly:

```text
PASS
PASS_WITH_LIMITATIONS
BLOCKED
FAIL
```

Requirements:

- Do not emit routine progress notifications unless current User/project/task authority explicitly opts in.
- One logical task must not emit separate completion/report-ready/push-complete/release-complete notifications.
- Collapse useful final facts into one compact terminal notification.
- Notification failure remains non-blocking and does not rewrite task truth.
- Uncertain delivery is not retried when duplication is possible.
- Do not create a scheduler/progress subsystem in this task.

# B. Same-message report/link presentation

# D. Optional dedicated-Bot automatic login

Implement exactly the accepted authority in:

`design/09_optional_bot_autologin.md`

## D1. Non-mutating feasibility preflight first

Before offering automatic login, inspect the current host without mutating security settings.

At minimum distinguish states equivalent to:

```text
autologin_supported
autologin_already_enabled_for_bot
autologin_disabled_by_user
autologin_unavailable_filevault
autologin_unavailable_managed_policy
autologin_unavailable_account_type
autologin_configuration_failed
```

Do not infer support merely because a command exists.

Current Apple platform constraints include hosts where automatic login is unavailable, notably FileVault-enabled systems, organization/profile restrictions, and some account/login configurations. Treat these as host constraints.

Never disable FileVault, weaken SIP/TCC, remove account security, or alter organization policy to force automatic login to become available.

## D2. Explicit ask_human authorization

If and only if automatic login is technically available and the exact target is the configured dedicated **non-admin** human-in-loop Bot user, ask one semantic decision before enabling it.

Use two stable choices equivalent to:

```text
enable_bot_autologin
manual_bot_login
```

The prompt must state compactly:

- automatic login reduces post-reboot manual work;
- it applies only to the dedicated Bot user, never the primary/admin account;
- it has a physical-access security trade-off because a restarted Mac may enter that Bot session without manual login;
- human-in-loop will not disable FileVault/SIP/TCC or capture Apple/macOS credentials to enable it.

Do not set a recommended choice by default.

If the User chooses `manual_bot_login`, preserve the current safe fallback and do not ask again on every setup/run.

If the User chooses `enable_bot_autologin`, proceed with the safest supported configuration path below.

## D3. Automatic implementation after approval

After `enable_bot_autologin`, Codex/setup should automate all safely automatable steps.

Hard requirements:

- target identity must be proven to be the configured dedicated Bot user;
- Bot account must be non-admin;
- never target the primary user, an administrator, root, or arbitrary caller input;
- use public/supported macOS mechanisms where available;
- do not use private loginwindow injection/private frameworks or security bypasses;
- no persistent privileged helper or broad sudo rule;
- configuration must be idempotent and independently verifiable.

If macOS requires account-password or administrator authentication, the secret may be entered only through an appropriate **native macOS authentication/UI surface**. Codex/human-in-loop must not read, echo, persist, log, report, place in environment variables, shell arguments/history, MCP payloads, repo files, temp files, or plaintext configuration any macOS/Apple password or 2FA secret.

If fully automatic configuration would require insecure credential capture or an undocumented/private mechanism, do **not** fake full automation. Automate navigation/preflight/state checking and let the User enter the secret in the native macOS surface once, then resume and verify automatically.

## D4. Unsupported-host fallback

If FileVault, managed policy, account type, or another real host constraint makes automatic login unavailable:

```text
DO NOT change the security constraint
DO NOT repeatedly ask the User for an impossible option
DO NOT mark human-in-loop setup as failed solely for this reason
```

Use the existing fallback:

```text
Mac reboot
→ BOT_SESSION_LOGIN_REQUIRED
→ User logs into dedicated Bot macOS user once
→ User returns to primary account
→ existing health predicates recover
```

This is session re-establishment, not reconfiguration.

## D5. Preference/state ownership

If a non-secret product preference/state is needed to avoid repeated prompts, store only the minimum safe value required, such as the selected mode/state. Never store authentication secrets.

The implementation must be able to distinguish at least:

```text
user chose automatic and host remains configured
user chose manual
host cannot support automatic
host configuration drifted
```

Do not create a second configuration universe or couple this to `HUMAN_IN_LOOP_HOME`.
