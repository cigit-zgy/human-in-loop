### 4. Add external `imsg` adapter

### 5. Enforce the absolute no-carrier boundary

All direct Apple Messages sends must be constructed as explicit iMessage-only sends. The effective command/adapter request must include explicit iMessage service selection and defense-in-depth no-SMS fallback behavior consistent with the inspected `imsg` contract.

Production code must have no reachable path that selects or falls back to:

```text
auto
sms
SMS
MMS
RCS
carrier relay
paid gateway
```

The settings UI must not expose a carrier-mode toggle.

A destination that cannot be confirmed/used as iMessage fails closed as `recipient_not_imessage` or the equivalent explicit health state. It never retries over a carrier service.

Add focused tests that would fail if `--service auto`, `--service sms`, or SMS fallback enters the iMessage send builder.

### 6. Implement the structured iMessage renderer

Initial iMessage support is limited to the bounded structured confirmation profile in `design/01_interaction_protocol.md`.

Enforce:

```text
title                       ≤ 60 Unicode scalar values
question/summary            ≤ 300
context fields              ≤ 5
one context value           ≤ 120
choices                     2–6
one choice label            ≤ 80
complete rendered text      ≤ 1200
outgoing decision images    ≤ 1
```

Do not silently truncate decision-critical fields. If the critical representation cannot fit, mark iMessage unsupported for that request and send nothing on iMessage while allowing Feishu to continue.

General free-form/multi-question/form interactions are not partially downgraded into iMessage.

### 7. Implement strict request correlation and reply parsing

Render a short collision-safe token derived from the canonical request id and require the inbound reply grammar:

```text
<TOKEN> <OPTION_NUMBER>
```

Example:

```text
7F32 1
```

Bare numeric replies are invalid. Do not use fuzzy/NLP intent parsing.

Inbound validation must establish:

```text
incoming message
AND configured direct chat/peer
AND exact token maps to one active request
AND option number is valid
AND request has not already terminated
```

Map the numeric position back to the canonical stable choice identity before delivering the result to the coordinator/Agent.

Malformed, stale, ambiguous, self-authored, wrong-chat, reaction-only, image-only, and late messages must not resolve a request.

### 8. Implement optional decision-image sending

The iMessage renderer may send at most one caller-supplied decision image when already present in the canonical request and admitted by design:

```text
PNG or JPEG
≤ 5 MiB
≤ 1 image
```

The renderer never creates/selects an image itself.

Do not use an attachment route that can fall back to MMS/carrier delivery. If the image is unsupported and the text alone is insufficient for a safe decision, skip iMessage for that request. Incoming images do not resolve a confirmation in this task.

### 9. Configuration and health

Settings should expose only:

```text
Feishu
Apple Messages (iMessage only)
```

For Apple Messages, provide the smallest setup/configuration needed for one existing direct iMessage peer/conversation. Prefer a verifiable stored handle + resolved chat identity over free-form repeated recipient selection.

At minimum distinguish health states equivalent to:

```text
not_configured
imsg_missing
permission_missing
messages_unavailable
recipient_not_imessage
watch_failed
send_failed
ready
```

Do not hide `recipient_not_imessage` inside a generic network error.
