# Implement copy-friendly iMessage decision spacing

## Mission

Project design/Skill Markdown already defines the desired presentation. Implement that contract in the maintained iMessage renderer and its tests.

This task changes presentation only. It must not change semantic choice IDs, token allocation, reply parsing grammar, correlation, watcher cleanup, iMessage-only transport, or public MCP tools.

## Authority

Fresh-fetch and read only directly relevant owners:

```text
AGENTS.md
design/10_mobile_reply_and_link_presentation.md
SKILL.md
src-tauri/src/channels/imessage.rs
```

The accepted renderer contract is:

```text
one blank line between distinct logical blocks
one blank line between numbered choices
Reply:

<TOKEN>-1
```

Do not reinterpret this as a parser change. Canonical inbound reply remains exactly `<TOKEN>-<OPTION_NUMBER>` after whole-message trim.

## Required implementation

Update `render_confirmation_with_config` so a normal decision renders equivalent to:

```text
[HIL · 48273]

Codex · project

<optional context block(s), preserving current compact semantics>

<detail/body>

<question>

1  First choice

2  Second choice

Reply:

48273-1
```

Requirements:

- distinct blocks separated by exactly one empty line;
- choices separated by one empty line;
- no trailing accidental blank-line explosion;
- `Reply:` is its own block;
- the copyable token-option string is the final standalone block;
- meaningful multiline `detail` remains byte/line faithful under the existing normalization rules;
- current decision budgets count the actual rendered string and remain fail-closed;
- compact single-line normalization of source/question/context/choice labels remains unchanged unless spacing alone requires test updates.

Update `diagnose_rows` and any other parser/diagnostic that currently assumes `Reply: <TOKEN>-1` is one line. It must recognize only the new canonical render, without relaxing reply correlation.

## Tests

Update/add tests proving at minimum:

- canonical renderer exact string has blank lines between source/question/each choice/reply label/token;
- token line is the final line and equals `<TOKEN>-1`;
- `Reply:` and token are separated by one empty line;
- multiline detail remains preserved;
- 2–6 choice counts still work;
- configured/default rendered budgets are recalculated for the new spacing and fail closed at the true boundary;
- history diagnosis recognizes the new footer and still rejects malformed/ambiguous sends;
- inbound parser still accepts only canonical `<TOKEN>-<OPTION_NUMBER>` and rejects bare/fuzzy alternatives;
- no change to iMessage-only/no-SMS send arguments;
- token allocation/correlation/first-terminal-result behavior stays green.

Do not weaken tests merely to accommodate changed character counts; update exact expected boundaries from the new canonical string.

## Non-goals

Do not:

- change token grammar or token derivation;
- accept bare digits on iMessage;
- alter ask_human/notify_human public surface;
- change watcher/correlation semantics;
- add transport fallbacks;
- change link-preview behavior;
- redesign budgets/security limits;
- change WME project code in this task.
