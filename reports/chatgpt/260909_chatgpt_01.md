## Incident already diagnosed

A real external project attempted to use the released machine-wide human-in-loop integration and failed before doing any scientific/data mutation:

```text
ask_human -> NoAvailableChannel
notify_human -> FAILED
```

The affected upstream task correctly failed closed with zero records written.

Root cause has already been established by local diagnosis:

```text
legacy Codex MCP registration
→ HUMAN_IN_LOOP_HOME points to an old isolated MCP runtime home
→ that stale config has Feishu disabled + iMessage disabled
→ coordinator sees zero available channels
→ NoAvailableChannel
```

At the same time the canonical runtime was healthy:

```text
interactive CLI -> canonical config -> iMessage READY
Bot session -> READY
Messages account -> READY
Bot worker/socket -> READY
Automation/TCC -> READY
macOS setup -> COMPLETE
```

The machine has already been recovered by removing only the managed legacy `HUMAN_IN_LOOP_HOME` override. Do not redo that recovery unless fresh inspection proves it regressed.

## Accepted architecture

Do **not** remove MCP.

The accepted production split is:

```text
Skill
= policy: when Codex must ask_human / notify_human

MCP
= primary structured invocation surface

canonical human-in-loop config + daemon
= shared runtime/channel state

CLI
= recovery/debug/fallback surface
```

MCP and CLI may have different process lifecycles, but they MUST NOT own separate product-managed human-in-loop configuration homes.

The human-in-loop-managed Codex MCP registration must use the same canonical runtime configuration as CLI/daemon.

Known legacy product-managed override:

```text
HUMAN_IN_LOOP_HOME = $HOME/.local/share/human-in-loop-codex
```

Equivalent home-resolved forms of that known legacy path are migration debt.

Unknown User-authored custom `HUMAN_IN_LOOP_HOME` values are **not** automatically owned by this project and must not be silently deleted or overwritten.

## 2. Implement managed legacy migration

Modify the existing Codex MCP install/update integration so that installing or updating human-in-loop performs a narrow migration of **only** the known project-managed legacy runtime-home override.

Required behavior:

```text
managed legacy HUMAN_IN_LOOP_HOME
= $HOME/.local/share/human-in-loop-codex
→ remove the env entry
→ MCP falls through to canonical human-in-loop runtime config
```

Requirements:

- detect the known legacy path without hard-coding a specific username;
- support the actual path representation produced by prior project code/configuration;
- remove only the owned legacy `HUMAN_IN_LOOP_HOME` key;
- preserve all unrelated MCP env keys, including PATH;
- preserve unrelated Codex config content/comments/order as far as the existing `toml_edit` integration contract supports;
- repeated install/update must be idempotent;
- a fresh install must never create a separate `human-in-loop-codex` runtime home;
- uninstall behavior must not remove unrelated User config.

Unknown custom runtime-home behavior:

```text
HUMAN_IN_LOOP_HOME = some other User-chosen path
→ do NOT silently remove or replace it
```

If the current installer cannot distinguish ownership safely, fail closed or surface an explicit migration state rather than guessing.

## 3. Canonical-config invariant

Add/adjust implementation checks so the project-owned Codex MCP integration cannot regress into a second configuration universe.

The product invariant is:

```text
CLI + MCP + daemon
→ same canonical human-in-loop configuration
```

Do not solve this by copying channel configuration into `$CODEX_HOME/config.toml`.
Do not embed recipient identity, Apple Account details, Feishu credentials, or any transport secret in the MCP registration.

## 4. Improve NoAvailableChannel observability

Keep fail-closed public decision semantics unchanged. Do not synthesize approval and do not broaden the MCP public tool schema merely for this hotfix.

When a confirmation falls back because no channel is available, daemon-side diagnostics must safely record why each maintained candidate was unavailable at a coarse level.

Target form is equivalent to:

```text
no_available_channel:
  popup=unavailable
  feishu=disabled
  imessage=disabled
```

or, when applicable, another stable non-secret reason such as:

```text
imessage=not_configured
imessage=worker_unavailable
imessage=automation_denied
imessage=watch_failed
```

Requirements:

- no recipient/email/phone number;
- no chat id/GUID/row id;
- no Apple Account value;
- no Feishu credential/user id;
- no message body/content;
- no raw private config dump;
- reason logging must not materially delay the fallback;
- existing `ConfirmFallbackReason::NoAvailableChannel` may remain the wire-level fallback enum.

Use existing channel health/readiness owners where possible; do not invent a second health model.
