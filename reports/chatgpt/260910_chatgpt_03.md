## Scope A — numeric correlation token with hyphen reply

Replace the phone-facing historical reply syntax:

```text
7F32 1
```

with the canonical new syntax:

```text
48273-1
```

### Token contract

The token remains mandatory and remains a correlation identifier rather than an authentication secret.

Required behavior:

```text
ASCII decimal digits only
first digit 1-9
no leading zero
normal token length = 5 digits
deterministic derivation from canonical request identity using the existing SHA-256/hash primitive
collision-safe among currently pending requests
same active request retains the allocated token
no new RNG/dependency required
```

Five canonical decimal digits provide 90,000 normal values (`10000..99999`), not less than the historical four-hex-character namespace of 65,536 values.

If a five-digit candidate collides in the active registry, extend deterministically by two decimal digits at a time:

```text
5 -> 7 -> 9 -> ...
```

Use the existing salted-rehash principle if more deterministic material is required. Never resolve a collision by reusing an active token.

The exact internal decimal extraction method is implementation detail, but it must be deterministic, simple, dependency-free, reasonably distributed for non-secret correlation use, and covered by stable fixtures.

### Render contract

New messages render only the new form:

```text
[HIL · 48273]
Codex · human-in-loop
...

1  Accept
2  Stop

Reply: 48273-1
```

Do not render a hexadecimal token, a space separator, or a bare-digit reply instruction.

### Parse contract

After trimming only outer whitespace around the whole incoming message, accept the canonical grammar:

```text
<TOKEN>-<OPTION_NUMBER>
```

The token must be decimal-only, no-leading-zero, correspond to one currently pending request, and the option must be in range for that request.

Reject at minimum:

```text
48273 1
48273 - 1
48273--1
48273_1
A7F3-1
1
04827-1
48273-0
48273-7 when only <=6 choices exist
extra prose around a reply
```

Do not add fuzzy intent parsing.

Do not implement the previously discussed bare `1..5` shortcut in this task. The User chose mandatory token correlation with lower keyboard cost instead.

### Correlation non-regression

After syntax parsing, preserve every existing correlation predicate:

- same configured direct chat;
- message strictly after request send/cursor boundary;
- incoming peer rules for production distinct-account topology;
- sent GUID / reply-to GUID checks;
- active token maps to exactly one request;
- valid choice ledger mapping;
- request not expired/terminal/cancelled;
- reaction/attachment-only rejection;
- duplicate and late reply rejection;
- exactly one terminal winner;
- watcher/request cleanup.

Do not weaken concurrency or exactly-once semantics to simplify the parser.
