## Scope

Prepare the next candidate as a narrow notification/onboarding polish only.

### A. Default proactive-message policy

Machine-wide default:

```text
real unresolved semantic decision
→ ask_human

normal terminal task state
→ at most one notify_human attempt

ordinary progress / heartbeat / percentage-complete
→ zero proactive notifications
```

Progress notifications may exist only when explicitly opted in by current User/project/task authority. Do not create a scheduler or progress subsystem in this task.

A single logical task must not emit separate completion/report-ready/push-complete/release-complete notifications. Collapse useful terminal facts into one compact terminal message.

Terminal states remain exactly:

```text
PASS
PASS_WITH_LIMITATIONS
BLOCKED
FAIL
```

Notification failure remains non-blocking and must not rewrite the established task verdict. Uncertain terminal delivery must not be retried when duplicate delivery is possible.

### B. Same-message locator presentation

Keep the existing MCP `locator` field and public schemas unchanged.

Current notification rendering appends a bare locator as its own unlabeled line. Change only presentation so a locator is rendered inside the same application message as a semantic line:

```text
Report: <locator>
```

For HTTP(S), preserve the raw URL exactly after `Report: ` so Apple Messages and other clients may auto-detect it as tappable.

Do not send a second application message for the link. Do not use Markdown link syntax. Do not claim control over Apple Messages rich-link-preview behavior.

If a stable renderer locale is already available at this boundary without architectural work, `报告：` may be used for Chinese; otherwise use stable `Report:`. Do not add a localization subsystem in this task.

Update notification length tests/budget handling only as mechanically necessary for the added label. Do not silently truncate.

### C. Onboarding/reboot documentation clarity

Do not redesign the macOS transport.

Clarify public docs/README from the existing `design/07_macos_runtime_deployment.md` authority:

- first-time iMessage onboarding is one-time setup;
- ordinary operation after `SETUP_COMPLETE` requires no repeated admin password, Keychain password, TCC grants, account switching, or reconfiguration;
- sleep/lock does not require re-onboarding;
- reboot does **not** require reconfiguration;
- after a reboot, if the dedicated Bot graphical/login session is absent, the only normal human recovery action is to establish that Bot login session once;
- existing Bot Apple Account sign-in, Messages activation, TCC grants, signing identity, recipient/channel config, MCP registration, and Skill pin are reused unless health proves that specific state was genuinely lost.

The public minimum iMessage setup should be described as conceptually:

```text
1. install human-in-loop
2. have/create one dedicated standard macOS Bot user
3. sign that Bot user's Messages.app into one distinct Bot Apple Account
4. return to primary user and run one human-in-loop setup/bootstrap command
5. grant only the consolidated macOS privacy permissions that setup reports as missing
6. complete one real notification/reply qualification
7. SETUP_COMPLETE; ordinary use thereafter is unattended
```

Do not expose internal HOME/socket/chat GUID/signing implementation details as required user configuration.

Where current setup already auto-detects or derives values, documentation must not ask the user to configure them manually.

Do not attempt to automate Apple Account credentials/2FA or bypass macOS TCC. Do not enable macOS automatic login as a product default.
