## Incident / root cause

A real `wastewater-model-evolution` production review request remained fail-closed with:

```text
ask_human -> NoAvailableChannel
```

while v0.1.1 itself had already proven:

- canonical config shared by CLI/MCP;
- iMessage health `ready`;
- macOS setup `COMPLETE`;
- one real short installed-Codex-MCP `ask_human` round trip PASS;
- one terminal installed-MCP `notify_human` dispatch SENT.

The second independent root cause is payload capability:

1. the WME caller supplies a legitimate multiline Chinese Human Review Card as `ask_human.context`;
2. current MCP mapping compacts that string into one `ConfirmField` line;
3. current iMessage confirmation renderer limits compact context lines to 80 Unicode characters and total rendered content to 700;
4. substantive review cards therefore fail before transport mutation and the coordinator ultimately reports `NoAvailableChannel`.

This is a `human-in-loop` interface capability defect. **Do not fix WME by deleting scientific evidence or shrinking its review card to fit the old 80-character context limit.**

# Required implementation

## 1. Public MCP `ask_human` optional multiline `detail`

Add an optional public input field:

```text
detail: string | omitted
```

Semantics:

- `detail` carries substantive evidence/body needed for the human decision;
- omission is fully backward-compatible;
- existing `question`, `choices`, `context`, `recommended_choice`, `request_id`, repository identity and result schema remain compatible;
- do not add a third MCP tool;
- successful result remains exactly the existing transport-independent result shape.

Mapping requirement:

```text
params.detail
→ canonical ConfirmDetail body
```

Preserve meaningful multiline structure. Do not normalize detail with a whole-string `split_whitespace()` or collapse paragraph/newline structure into one line.

It is acceptable to normalize line endings (`CRLF`/`CR` → `LF`) and remove only irrelevant outer blank-space according to one documented/tested rule. Do not rewrite substantive internal text.

`context` retains its existing compact metadata role and existing compatibility behavior. Do not silently reinterpret old `context` as unlimited detail.

## 2. iMessage multiline rendering

Extend the existing iMessage confirmation renderer to render canonical detail/body as multiline plain decision evidence.

Expected phone ordering is structurally equivalent to:

```text
[HIL · TOKEN]
<source/repository>
<compact context metadata when present>

<multiline detail when present>

<concise question>

1  <choice>
2  <choice>
...

Reply: TOKEN 1
```

Exact whitespace may follow existing style, but:

- meaningful detail newlines must survive;
- compact context line limits must not be applied to the whole detail body;
- no evidence required for a decision may be silently omitted;
- no silent truncation;
- the existing strict correlation/token/choice semantics remain untouched.

## 3. Configurable operational payload budgets

The product default must support real substantive decisions without turning transport into an unbounded document channel.

Add backward-compatible iMessage configuration following existing serde/config conventions with these semantics:

```text
decisionDetailMaxChars   default = 1000 Unicode characters
decisionRenderedMaxChars default = 1500 Unicode characters
```

Use the repository's existing naming/serialization conventions. Existing configs missing these fields must receive the defaults automatically without migration prompts.

User-configured values may be larger, subject to these defensive ceilings:

```text
ABSOLUTE_DETAIL_MAX_CHARS   = 4500
ABSOLUTE_RENDERED_MAX_CHARS = 5000
```

Validation requirements:

- count Unicode scalar/character semantics consistently with current renderer, not UTF-8 bytes;
- operational values must be positive;
- `decisionDetailMaxChars <= decisionRenderedMaxChars`;
- values above the absolute ceilings are invalid/fail closed; do not silently clamp;
- do not silently rewrite the User's unrelated channel/config state;
- no new credential or secret is introduced.

A new GUI settings control is **not required** in this hotfix. The canonical config fields are sufficient. Do not broaden scope into a settings redesign.

## 4. Existing compact limits remain semantically narrow

Do not simply change:

```text
MAX_CONTEXT_LINE_CHARS 80 -> 1000
```

and call the task complete.

That would preserve the wrong model.

Keep compact context/metadata and choice/question structural limits reasonably bounded unless a directly affected test proves a minimal adjustment is required. Any such adjustment must be justified in the report and must not be used as a substitute for the new detail/body path.

## 5. Typed/redacted payload diagnostics

`NoAvailableChannel` remains the canonical fail-closed outcome when no decision surface succeeds.

Extend the v0.1.1 redacted observability boundary so payload incompatibility can be diagnosed without exposing the body.

At minimum distinguish fixed coarse reasons equivalent to:

```text
detail_too_long
rendered_text_too_long
invalid_decision_budget
```

Reuse existing typed diagnostic structures when possible; do not introduce raw free-form logging if a fixed enum/status is sufficient.

Forbidden in logs/reports/diagnostic payloads:

```text
detail/body text
question text when not necessary
recipient/email/phone
chat id/GUID/row id
token
message content
credentials
Apple Account identity
private config values
```

Do not weaken MCP privacy/result schemas to expose transport internals.

Verify that existing popup and Feishu confirmation paths either already consume canonical `ConfirmDetail.body_md` correctly or receive the minimal required adapter so the same decision evidence is available without semantic loss.

Do not redesign Feishu cards or popup UI. Make only the minimal compatibility change actually required.
