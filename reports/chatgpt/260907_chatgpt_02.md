### 2. Add explicit identity mode

Represent the Apple Messages reply topology minimally as:

```text
distinct_peer
same_account
```

Do not infer physical device provenance.

The runtime/user configuration must be able to designate `same_account` for a handle belonging to the same Apple Account used by the Mac.

Keep the existing distinct-peer behavior:

```text
is_from_me == false
```

For `same_account`, `is_from_me` is not a rejection criterion by itself. The strict post-send correlation contract below becomes decisive.

Avoid speculative abstractions or a generic identity-provider framework.

### 3. Support first-use bootstrap without an existing chat

Current implementation blocks configuration when no deterministic existing direct conversation is present. Replace that peer-only assumption with the accepted bootstrap semantics.

When the configured User-approved handle has no resolvable direct chat:

- preserve it as private local runtime configuration;
- expose/recognize the design state equivalent to `bootstrap_required`;
- do not require the User to manually create a conversation first;
- do not send a separate probe merely to create history.

The first actual supported structured confirmation is the bootstrap message.

Before mutation:

```text
allocate the normal collision-safe request token
establish a pre-send database/cursor/time boundary
render the normal bounded canonical confirmation
```

Then use only the production direct-send path equivalent to:

```text
imsg send --to <private-approved-handle> --service imessage --no-sms-fallback ...
```

Never use `auto`, `sms`, SMS fallback, MMS, RCS, or carrier relay.

After a reported successful iMessage mutation, resolve from documented local data exactly one direct iMessage conversation containing the resulting request. Establish and persist only after deterministic resolution:

```text
chat_id / chat_guid
service = iMessage
sent message row id when available
sent message guid when available
```

If the recipient cannot be used as iMessage, resolution is ambiguous, service is inconsistent, or the mutation outcome is uncertain, fail closed according to the accepted design. Do not blindly resend an uncertain mutation.

### 4. Establish a strict post-send request boundary

For every iMessage request, retain sufficient ephemeral request state for correlation:

```text
canonical request id
collision-safe token
resolved chat id/guid
send/cursor boundary
sent message row id when available
sent message guid when available
active/terminal request state
```

Use documented `imsg` JSON/NDJSON fields. Do not parse presentation text when machine fields exist.

The receive path must not accept older chat history or the outgoing request itself.

If a reply can arrive between post-send resolution and watcher startup, recover it from the bounded post-send cursor/history rather than creating a race window.

### 5. Implement same-account reply correlation

For `same_account`, a candidate may have `is_from_me=true` or `false`, but it is valid only when ALL applicable checks succeed:

```text
same configured direct chat
AND strictly after the request send/cursor boundary
AND candidate guid != sent request guid when both exist
AND text exactly matches <TOKEN> <OPTION_NUMBER>
AND token resolves to exactly one active request
AND option number is valid
AND request is still active
AND not reaction-only
AND not attachment/image-only
```

If `reply_to_guid` exists on the candidate:

```text
reply_to_guid must equal sent request guid
```

An inline Messages Reply is additional evidence, not mandatory normal UX.

Do not accept fuzzy natural-language answers. Bare numeric replies remain invalid.

The outgoing structured request must never resolve itself as an answer even if Messages later updates/re-emits its row.

Duplicate, stale, wrong-chat, pre-send, malformed, reaction, attachment-only, and late messages remain non-terminal.

Exactly one terminal answer may win through the existing coordinator/preemption semantics.

### 6. Preserve distinct-peer behavior

Do not regress the original distinct-peer path.

```text

```

## Acceptance criteria

PASS requires all of the following:

1. Same-account is an explicit supported runtime topology without a second Apple Account.
2. A configured same-account handle may reach `bootstrap_required` without an existing direct chat.
3. The first real supported request can create/resolve the direct conversation using explicit iMessage-only send semantics.
4. No reachable bootstrap or normal send path selects/falls back to SMS/carrier transport.
5. Post-send row/GUID/cursor state prevents the outgoing request and pre-existing history from resolving a request.
6. A strict same-account `is_from_me=true` token reply can be accepted when all correlation checks pass.
7. Distinct-peer self-message rejection remains intact.
8. Wrong/stale/duplicate/reaction/attachment/late candidates remain non-terminal.
9. Real Mac+iPhone same-Apple-Account E2E returns the chosen canonical option to AskHuman and cleans up the watcher.
10. Private recipient and Messages contents remain absent from committed evidence.
11. Required automated/build/static verification passes.
12. Task branch is pushed, clean, and fresh-fetch local/upstream/FETCH_HEAD equality is demonstrated.

Use `BLOCKED` only for a genuine remaining external/manual prerequisite that cannot be resolved under the accepted design. Use `FAIL` for a violated contract that cannot be repaired within this task.
